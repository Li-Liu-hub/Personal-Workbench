# 个人办公台开发规范

## 原则与边界

极致轻量，极致简约。以可持续维护和真实个人使用为依据，不为新增一个页面引入独立后台服务或通用框架。仓库只有一个客户端：根目录 `personal-desk` 核心库负责数据与业务，`desktop/` 的 Tauri + React 客户端负责界面；核心库不得依赖任何 UI 框架。

## 代码分层

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 核心库 | 根目录 `src/`（Cargo 包 `personal-desk`） | 数据访问与增量迁移（`src/db.rs`、`src/db/`）、领域模型与规则（`src/model.rs`、`src/library.rs`、`src/contacts.rs`、`src/essays.rs`、`src/websites.rs`、`src/tags.rs`、`src/theme.rs`、`src/launcher.rs`）、导入导出（`src/import.rs`、`src/export.rs`）、更新与自启、图片、私网账号库与 MongoDB 文档发布；不依赖 egui、React 或 Tauri |
| 桌面端状态 | `desktop/src-tauri/src/state.rs`、`lib.rs`、`main.rs` | 数据目录解析、数据库初始化、单实例、主窗口、命令注册与命令行模式；不写业务规则 |
| 桌面端命令 | `desktop/src-tauri/src/commands/*.rs` | Tauri 命令：参数转换、访问 `state`、调用核心库 API；不重复实现校验或 SQL |
| 前端页面 | `desktop/src/*Page.tsx`、组件与 hooks | 页面与交互，通过 `invoke` 调用命令；业务校验以核心库为准，前端只做即时反馈 |
| 测试 | 各模块内联 `#[cfg(test)]`、`tests/`、`desktop/src/*.test.tsx`、`scripts/tests/` | Rust 单元与集成回归、前端 vitest、Python 导入脚本回归 |

新功能按「核心库模型与校验 → 数据库事务与迁移 → Tauri 命令 → 前端页面」的顺序接入，避免为了减少行数把不相关逻辑塞进 `utils` 或直接写进命令层。现有模块只在有明确收益时拆分，保持行为和数据兼容。

## 持久化与升级

- 新表和新列采用增量升级，保留旧记录和未知设置；不得以清库重建解决版本问题。
- 多表写入放在事务内。用户编辑失败时保留草稿，界面只在提交成功后更新已保存状态。
- 内置数据有稳定 ID 和版本标记。导入与标记遵循可重放原则，同 ID 不覆盖个人修改；删除内置条目保留墓碑，后续升级不会复活。
- 可并行编辑的数据使用修订号检测冲突，不让旧界面覆盖较新的内容。历史练习快照保持不可变。
- 新模块必须进入模块导出和全部导出。快捷路径只保存地址，不能递归打包它们指向的外部文件夹。
- 真实数据验证先建立一致快照并检查完整性，升级和导出验收在副本上执行；更新包只替换程序。

初始语言为 JavaScript、Java、C、C++、Rust、Go、Linux、MySQL。分类按用途组织，如基础语法、集合与容器、函数与对象、异常与资源、异步与并发、查询与聚合。用户可增加语言与分类，不把分类写死为只能选择初始值。

每条包含稳定 ID、语言、分类、类型、标签、名称、说明、语法、示例、要点和参考链接。基础示例以 Java 17、C17、C++17、Rust 2024、Go、现代 JavaScript、GNU/Linux、MySQL 8.0+ 为主要语境；特殊版本前提写在要点。示例多数是使用片段，按要点补充导入、外围函数或示例表；不能声称所有片段都可单独运行。

示例及中文解释为项目编写，参考链接指向语言/工具维护者文档。集合说明应交代顺序、空值、所有权或迭代失效等相关条件。SQL 与 Linux 命令只用于查阅和复制，指令页不执行命令。

Java 生态按语言核心、锁与内存模型、JUC、现代并发、JVM、Spring 容器 / AOP / 事务、Boot、Web、持久化、安全、分布式、中间件、构建测试、交付诊断等层次组织。新增主题先检查覆盖缺口、前置知识与版本，不只堆积 API 名称。JVM 历史实现与现行规范分开；例如锁升级路径、虚拟线程 pinning 必须注明具体版本前提。框架用主流基线给出用法，不把参考页当前版本自动套到旧项目。

每条知识写清“解决什么问题 → 机制 → 具体片段或场景 → 常见失败与适用边界”，并链接维护者资料。练习应给出可判断的任务、输入 / 代码或场景及与任务一致的评分要求，通过 `knowledge_ids` 精确关联；不要把同一段泛泛要求复制成所有题干。示例只验证实际执行过的集合，不将片段测试推广为整个框架集成通过。

增量资源为 `assets/java_ecosystem.json` 和配套练习，使用独立版本标记；重复导入不能覆盖已修改条目、恢复已删除内容或改写成绩。界面名称为“百科全书”，原 `reference` 模块名、数据库表名及知识点 ID 保持兼容。

## 性能约定

- 前端渲染不重复加载整份正文、照片原件或数据库列表；查询结果缓存需与搜索、筛选和写入操作一致失效。
- 大列表仅绘制可见行。保留完整滚动高度，控件使用稳定记录 ID，滚动离屏不会丢弃编辑草稿。
- 内置数据只在首次或新版本导入；菜单只查所需字段。局部配置读取使用单键接口，不反复读取整份设置。
- 文件内容索引使用 SQLite FTS5 trigram；索引只覆盖文件标题、路径和正文，账号密码等私密字段不进入索引。显示列表只取摘要，选中后才读完整内容。
- 文件、网络、数据库等耗时工作放后台，并有界面状态反馈；不要用长时间阻塞等待冻结界面。
- 性能结论附工作量、构建模式和对照方法；普通自动测试验证可见行数量、最后一行可达与数据一致性，避免断言某个机器耗时阈值。

## 界面与交互

遵循现有浅色风格、紧凑工具栏和固定操作区。列表的表头、文字及操作按共用几何对齐；不使用不同页各自凑内边距的方法。分类与搜索组合生效，空结果应可清空筛选。未保存编辑不能因为切换条目而被静默丢弃。

列表单行字段首次获得焦点时全选现有内容，输入即替换，不因点击直接修改数据；仍保留保存 / 取消。改变筛选不能丢草稿，取消编辑后应回到当前筛选结果，不能显示游离于结果列表外的旧详情。

## 检查与发布

项目采用原入口持续更新。用户始终打开 `dist/个人办公台.exe`，通过现有更新机制升级；不要另建“某功能版”“本次可运行版”等独立程序入口。`dist/updates` 下的版本载荷用于安装更新，不作为用户启动入口。原程序运行时先发布更新，保留当前窗口和未保存内容，由程序内更新完成替换与重启。

提交前执行唯一检查入口：

```powershell
.\scripts\verify.ps1
```

该入口包含 Rust 格式（根 crate 与 desktop 后端）、Clippy（debug 与 release 库）、Rust 回归、`desktop` 前端构建 / lint / vitest 回归、Tauri 后端 Clippy 与 Python 回归；`scripts/build.ps1` 必须先通过同一入口，才会构建 Tauri 发布程序、复制到 `dist/个人办公台.exe` 并写入本机更新清单。正式发布包由 `scripts/package-release.ps1` 生成，GitHub Release 由 `scripts/publish-github-release.ps1` 创建或更新。前端 lint 当前只要求 0 error，既有 warning 仍会输出，不要把 lint 结果写成无警告通过。

测试使用临时目录和模拟数据，不打开个人数据库。新增持久化模块至少覆盖增删改查、搜索 / 分类、重启、升级不覆盖、导出以及失败保留原数据；前端改动要补 vitest 回归。真实 MySQL、MongoDB、安装更新和发布权限相关验证按需在对应环境执行，不把未运行的环境或忽略项算作普通回归通过。

发布更新前检查新页面在常用窗口尺寸的预览，构建正式版，在旧数据副本完成升级和完整导出核对，再发布带版本与哈希的更新包。版本号五处必须一致（根 `Cargo.toml`、`desktop/src-tauri/Cargo.toml`、`desktop/src-tauri/tauri.conf.json`、`desktop/package.json`、`assets/release_history.json` 首项），由 `tests/version_consistency.rs` 回归。保留运行中的旧程序，由用户点击更新；源码、文档与测试一起提交，推送后核对远程提交。

## 新功能接入清单

1. 定义独立模型与输入验证，选择明确的存储边界。
2. 增量建表/索引，编写事务、版本标记及冲突策略。
3. 在核心库补齐读写与校验后，添加 `desktop/src-tauri/src/commands/` 命令并在 `lib.rs` 注册；在 `desktop/src/App.tsx` 的导航与页面路由中接入，功能状态归入自己的页面组件。
4. 接入搜索、导出、空状态和已有快捷键，保留个人数据与草稿。
5. 添加行为回归、必要的性能验证、界面预览及 README 使用说明。
